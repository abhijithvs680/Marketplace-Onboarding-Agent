# Authentication

Five mechanisms. They are **not** interchangeable — each endpoint accepts a
specific subset, and picking the wrong one is the most common integration
failure.

| Mechanism | Header / param | `workflow.trigger` | `sys/api.v1` | Session pages (`workflow.exec`, `/ls/*`, the studio) |
|---|---|---|---|---|
| Session cookie (`tsid`) | cookie | — | yes (implicitly, via `session('uid')`) | **the only one** |
| JWT bearer | `Authorization: Bearer <jwt>` | yes | yes | — |
| Hash token | `hashtoken: <key>` | yes | — | — |
| Auth token | `auth_token: <token>` | yes | — | — |
| HTTP basic | `Authorization: Basic …` | yes | yes | — |
| Signed URL | `?signature=…` | — | yes | yes |

`$APP/sys/users/Authenticator.php` implements all of them;
`$APP/sys/http/Request.php::__get('User')` decides which one a request gets.

## Session cookie

The default, and the only thing the React Workflow Studio and every `/ls/*`
endpoint accept. Cookie name `tsid`, `Domain` = the tenant domain, `Secure`.
Sign in at `/user.signin` (`_dn=<return path>` for the post-login redirect).
`SESSION_TIMEOUT` is 10800 s in `options`; session storage is Redis db 1 plus
MySQL `viz_sessions`.

A localhost dev server does **not** share cookies with the platform host —
proxy same-origin and strip `Secure`/`Domain` from `Set-Cookie`. See
[workflow-ui.md](workflow-ui.md).

## JWT bearer

`$APP/sys/users/User.php::generateToken($deviceId = '')`:

```json
{ "fname": "First Last", "uid": 188, "email": "user@example.com",
  "exp": <issued + 86400>, "domain": "<Domain>", "persistant": "0" }
```

- Algorithm **HS256**, secret = `app()->Tenant->PrivateKey` (per tenant).
- Lifetime **24 hours**. A non-empty `deviceId` sets `persistant: "1"`.
- Also available inside any workflow template as `{user-token}`.

### Getting one

`POST /sys/api.v1` with `op=user.jwt.externalauth` (or `user.jwt.validate`,
which wraps it), authenticated by some other means — typically basic auth or an
existing session:

```
op=user.jwt.externalauth
args[deviceId]=<urlencoded JSON, e.g. {"devicenum":"web-1"}>
```

Response `Body`:

```json
{ "Id": 188, "FirstName": "…", "LastName": "…", "Email": "…",
  "CreatedAt": "…", "JWTtoken": "<jwt>", "refresh_token": "<64 hex>",
  "TenantId": 11, "ChatWorkflow": "…", "ExternalSocketServer": "https://localhost:8000" }
```

A missing `devicenum` becomes the literal `"unknown"`. The token is written to
`viz_sessions.refdata` keyed by `(sid = deviceId, uid, tid)`, and the refresh
token is stored by `tsessionInsert`.

`op=user.jwt.regentoken` refreshes. It is the one path where `decodeJWT` will
decode an **expired** token without verifying, specifically so a refresh can
work.

### Verification behaviour

`decodeJWT` maps JWT errors to HTTP codes itself and then throws:

| Condition | Status |
|---|---|
| expired (`ERROR_TOKEN_EXPIRED`, code 52) | **417** |
| signature/claim failure (code 60) | **401** |
| other decode failure | that code |

On `workflow.trigger` a malformed bearer is caught and answers **498**; an
`exp` in the past answers **417**. On `/sys/api.v1` the throw escapes and you
get a **500** — verified live. Do not treat 500 there as "server broken"; check
your token first.

The same secret signs the socket.io handshake (`socketio-jwt` with
`JWT_SECRET`), so one token authenticates both the API and the realtime
connection.

## Hash token

`hashtoken: <session key>`. The trigger reads the raw value from
`HTTP_HASHTOKEN`, loads it through `SessionEngine::read()`, `session_decode`s
it, and takes `$_SESSION['uid']`. It is a **reference to a stored session**, not
a self-contained credential — issued by the chat/kiosk flows, which pass it
through `set_user` on the socket.

## Auth token

`auth_token: <token>`. `Authenticator::_authenticateBytoken($signaturehash)`
resolves it to a uid. Accepted by `workflow.trigger`, and `genericpost` also
copies the header into the workflow's input row (masked in the debug log).

## HTTP basic

`Authorization: Basic base64(email:password)`. On `workflow.trigger` it is only
taken when `$_SERVER['PHP_AUTH_USER']` is also populated (i.e. Apache parsed it),
then `Authenticator::Authenticate()` runs the normal password check. On
`/sys/api.v1` the same pair is read straight from `PHP_AUTH_USER`/`PHP_AUTH_PW`.

Password policy knobs live in `options`: `PASSWORD_COMPLEXITY`,
`PASSWORD_LENGTH`, `PASSWORD_LOOKBACK`.

## Signed URL

A time-boxed, uid-bound signature on one exact URL. Generated by
`Authenticator::generateSignature($url, $uid, $persist = false, $expires = 300)`:

```php
$payload = [ $created, $expires, $uid, $url ];
$payload[] = hash_hmac('sha512', json_encode($payload), $tenant->PrivateKey);
return base64_encode(json_encode($payload));
```

Pass it as `?signature=<that>`. Verification requires
`created < expires && expires > time()`, an **exact** match on
`"https://" . Domain . "/" . RawPath`, and the HMAC to reproduce. On success the
request is logged in as that uid with `session('URLAuth') = true`.
`$persist = true` sets `expires = false`, which makes the window check fail — so
a persistent signature validates only through `validateSignature()`, which does
not log anyone in.

From inside a workflow: `{%sign <url>%}` mints one for the current user with a
60-second window. Use it for a download link you hand to a browser.

## Which endpoint accepts what

### `POST /workflow.trigger/<shortCode>`
`authorize()` requires the first block's `obj_id` to be **4200–4205**, then:

- `auth_required = "0"` (or unset) ⇒ **no credential at all**. The run executes
  as the uid stored in the trigger block's `block_properties['uid']`.
- `auth_required = "1"` ⇒ one of bearer / hashtoken / auth_token / basic. The
  resolved user is loaded, the session id regenerated, and `app()->init()` re-run.

After the run, if the caller had no pre-existing platform session the controller
calls `session_unset()` + `session_destroy()` — so a trigger call leaves nothing
behind.

### `POST /sys/api.v1` (and `api.v2`)
`Request::IsApi` is true **only** for a POST to exactly `sys/api.v1` or
`sys/api.v2`. Resolution order in `Request::__get('User')`:

1. `?signature=` present ⇒ URL auth
2. `Authorization: Bearer` ⇒ JWT
3. `PHP_AUTH_USER` + `PHP_AUTH_PW` ⇒ basic
4. otherwise `session('uid', 0)`

Then the service's own `authenticate()`/`authorize()` run. The status lives
**inside the JSON envelope**, not only in the HTTP status:

```json
{ "Echo": null, "Status": [401, "Unauthorized"], "Time": "…",
  "Errors": ["Invalid API Authentication Credentials."], "Body": null }
```

`execute()` sets `Access-Control-Allow-Origin: *` on this endpoint.

### `POST /workflow.exec/<id-or-shortCode>`
Session only — `$app->Request->User->Id <= 0` answers **401** and exits. An
unknown shortcode redirects to `/` (302) before the check.

### MCP server
Its own HTTP basic credential (`MCP_API_USER` / `MCP_API_SECRET`), unrelated to
platform users. It has no concept of a Vizru user — tenant scope comes from the
`tid` in the request body, which is why a caller holding the credential can
claim any tenant. See [mcp-server.md](mcp-server.md).

## Tenant resolution

`app()->Tenant` is derived from the request host. Relevant `options`:
`VIZRU_TENANT_DOMAIN`, `VIZRU_TENANT_ID`, `VIZRU_TENANT_NAME`,
`VIZRU_MULTI_TENANT`, `VIZRU_MATCH_TENANTINFO`, `VIZRU_COOKIE_DOMAIN`. Every
Mongo query carries `_tid` and every MySQL query `tid`; **`Tenant->PrivateKey`
is per tenant**, so a JWT minted for one tenant will not verify against another.

## Permissions

- `hasPermissionById($pid, $uid)` → MySQL `fUserHasPermissionById`. A super
  admin (`isSuperAdmin() == 9`) bypasses. A user whose `flags` lack `enabled`
  is redirected to sign-out mid-check.
- Workflow authoring/saving needs **1007** (`workflow.save`, `workflow.edit`).
- App-scoped checks go through `Livespace::permissionCheckByUid($lid, $uid)`;
  file download is app permission **113**.
- `viz_user_permissions`, `viz_user_groups`, `viz_user_tenants` hold the grants.

## Building a client

**Server-to-server:** mint a JWT once per day via `user.jwt.externalauth`,
send it as `Authorization: Bearer` to `workflow.trigger` endpoints whose trigger
block has `auth_required = "1"`. Store the `refresh_token`.

**Browser:** you have two options and they are genuinely different.

1. *Public trigger* — `auth_required = "0"`, and the workflow runs as the
   configured `uid`. Nothing to authenticate, but **the origin must be in the
   hard-coded CORS allow-list** in `Trigger.php` (currently
   `http://localhost:3000`, `https://baines.healthcare`, `*.vizru-ras.com`).
   Anything else gets no CORS headers.
2. *Same-origin* — serve the app from the platform host (as the Workflow Studio
   does) and let the session cookie work. No CORS, no token handling, and every
   `/ls/*` and `/sys/api.v1` endpoint becomes available.

Do not put a JWT in a public SPA bundle: it is a 24-hour, full-user credential
signed with the tenant key.
