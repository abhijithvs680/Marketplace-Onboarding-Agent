# The workflow model

## `VizWorkflow` (Mongo)

Verified keys on a live document:

```
_id, _tid, name, desc, short_code, w_objects, connection, full_objects,
enable_log, schedule, created-by, created-at, updated-by, updated-at, _flags
```

Plus, when set: `deleted` (the string `"true"` — soft delete), `reusables`,
`worker_job_id`, `container_id`.

| Field | Notes |
|---|---|
| `name` | **unique per tenant.** `workflow.save` refuses a duplicate with "Stencil name already exist". |
| `short_code` | generated by `aString::createShortCode($name)` = `strtolower(preg_replace('/[^a-zA-Z0-9]+/', '', $name)) . uniqid()` — so `"Entry to Agents"` becomes `entrytoagents6a6ddeed16161`. The stable external identifier; every entry point accepts `_id` **or** `short_code`. |
| `enable_log` | **inverted.** The engine writes logs when `enable_log != '1'`. New workflows get `1`, i.e. logging off. |
| `schedule` | `'1'` marks the workflow as scheduled (`workflow.getscheduledwf` filters on it). |
| `full_objects` | `json_encode($w_objects)` written alongside the array on every save. A denormalised copy — do not treat it as authoritative. |
| `deleted` | the **string** `"true"`. Every query carries `'deleted' => ['$ne' => 'true']`. |
| `reusables` | `{ fieldset: [ { input, required, notes }, … ] }` — declared inputs when the workflow is used as a reusable. |

The platform's own vocabulary calls a workflow a **"stencil"** in log messages
and some UI strings.

### `w_objects[]` — the blocks

```json
{
  "id": "4202_2",
  "type": "genericpost",
  "obj_id": "4202",
  "position": { "x": "120", "y": "340" },
  "icon_path": "/ui-themes/karma/images/svg/generic-get.svg",
  "source": 0,
  "target": "2055_3",
  "block_properties": { "label": "Entry", "auth_required": "0", … },
  "properties": { "field-mapping": [ … ] },
  "short_code": "…",
  "scheduler": "Yes",
  "scheduled_interval": "…",
  "clone_wf_id": "…"
}
```

- `id` is `<obj_id>_<sequence>`. `obj_id` is the palette id
  (`Leftblock.php`) — except for `livecloudfunction`, `dataset` and
  `executeworkflow`, where it is a Mongo ObjectId, and `livespace`, where it is
  `livespace-<kind>-<lid>-<fid>`.
- **`source == 0` marks the entry block.** `getActivity('')` returns the first
  block with `source == 0`; that is where every run starts.
- `target` is the next block's `id`, `0` when terminal.
- On a `condition`, `target_yes` / `target_no` replace `target`.
- `position` is written by `workflow.save` from the session's `xPos`/`yPos` —
  and they are transposed; see [workflow-ui.md](workflow-ui.md).
- `block_properties` is the block's configuration
  ([blocks.md](blocks.md)); `properties['field-mapping']` is the connection
  mapping. Both are **omitted entirely** when not arrays, so code must treat a
  missing key and `""` the same.

### `connection[]`

```json
{ "id": "2001_11-4202_2", "source": "2001_11", "target": "4202_2",
  "target_no": "", "target_yes": "4202_2" }
```

Redundant with `w_objects[].target` — `workflow.save` writes both, walking the
connections to stamp `source`/`target`/`target_yes`/`target_no` onto each block.
**The engine only reads the block fields.** A graph edited by writing `connection`
alone will not change execution.

Note a quirk visible in real data: `target_yes` is populated on non-condition
edges too (it mirrors `target`), so do not infer "this is a condition branch"
from its presence — check the source block's `type`.

## Execution logging

Two tiers.

**MySQL `viz_workflow_exec_log`** — one row per *run*:
`workflow_exec_id` (PK), `tid`, `uid`, `workflow_id`, `name`, `executed_from`,
`description`, `created_at`. Later updates add `exec_status`, `finished_at`,
`child_workflows`, `mode`.

- `mode` is `1` for master, `0` for child.
- `exec_status` starts `Failed` and is set to `Success` on completion — so an
  interrupted run stays `Failed`, which is the point.
- `executed_from` is a free string: `external` (trigger), `chat`, or whatever
  the caller passed.
- `child_workflows` accumulates `<childWfId>-<logId>,` entries.
- A deleted-mid-run workflow gets `exec_status = 'Workflow found deleted'`.

**Mongo `VizWorkflowLog`** — one document per *block*:

```json
{ "exec_order": 1, "log_master": 1, "workflowId": "…", "workflowName": "…",
  "target": 0, "activityid": "2001_2", "block_label": "", "block_name": "Get Parameters",
  "block_type": "datatransfer", "block_icon": "…", "function_id": "2001",
  "execution_time": 0.0764, "mem_reserved": "2 mb", "mem_used": "823.72 kb",
  "completed": "Yes", "debug_log": { "output": [] },
  "_tid": 11, "created-by": 188, "created-at": "…" }
```

`log_master` joins back to `viz_workflow_exec_log.workflow_exec_id`.
`debug_log` is the block's `debugLogData`, with two sanitisations: values over
2048 bytes or not valid UTF-8 become `** Data is not UTF-8 or is too large to
store **`, and `.` in keys becomes `*` (Mongo rejects dots in field names).
`livecloudfunction` gets extra key-rewriting on its nested output.

Read it back via `GET /workflow/log.debugdata/{logId}` →
`{ summary, blockInfo: { <activityId>: { block_type, block_name, block_label,
completed, execution_time, target, data } } }`. `completed` casing is not
stable — `Workflow-UI/src/lib/runStatus.ts` normalises it.

## Versions

`$APP/sys/workflow/Workflowversion.php`, collection `VizWorkflowVersions`.
`insertVersion($shortCode, $wConfs)` stores `{short_code, version, w_objects,
connection, note, deleted}`. The version number is `max(version) + 1` — but the
counting is off by one on the very first save (it only increments when more than
one document already exists), so treat `version` as an ordering key, not a count.

Endpoints: `POST /workflow.version`, and
`/workflow.versiondebugger/{id}` renders a **read-only** canvas for a snapshot.
In the React studio that surfaces as `#/debugger/<id>?version=<vid>`.

## Tags — how a workflow belongs to an app

`$APP/sys/workflow/Tags.php`, collection `VizTags`. A tag associates a
workflow's `short_code` with something else by type; `tag-type = 'livespace'`
with `tag-shortcode = <app short code>` is how a workflow is attached to an app.
`workflow.save` creates that tag automatically when `apps_shortcode` is posted.

`Tags::listTags($shortCode, 'livespace')` is what `Leftblock::getAppShortcode()`
uses to scope the palette to one app.

## Reusables

`$APP/sys/workflow/WorkflowReusables.php`. `insertReusables($wfId, $array)`
writes `reusables` onto the workflow document; `fetchReusables($wId, $meta,
$short_code)` reads it. The declared `fieldset` becomes the input form that the
`executeworkflow` dialog renders, and the values land in
`block_properties['reusable_params']`.

A reusable workflow appears in its own palette group. Endpoint:
`POST /workflow.reusables` with `{inputdata: {wid, short_code}, key: 'view'}`.

## Scheduling

`$APP/sys/workflow/Schedule.php`, collection `VizWorkflowSchedule`. A document
is `{workflow_id, minute, hour, day, command, created-by}` where `command` is a
full URL:

```
<base>/workflow.startcrontask/<workflowId>/user_id/<uid>
```

So a scheduled run is an HTTP self-call that impersonates the creating user.
Celery Beat (`receiver-celery-beat`) drives it; `workflow.getscheduledwf` lists
workflows with `schedule == '1'`. UI: `/workflow.schedule/{workflowId}`.

## Templates

MySQL `viz_template_workflows` ties workflows to a livespace template
(`Workflow\Settings::addWorkflowToTemplate()` via the stored procedures
`fLSTemplateWorkflowDelete` / `fLSTemplateWorkflowInsert`), keyed by
`lid`/`cid`/`fid`.

## Loading a workflow in PHP

```php
$wf = new \Sys\Workflow\Workflow($mongoId);        // constructor
$wf = new \Sys\Workflow\Workflow();
$wf->loadById($mongoId);                          // request-cached
$wf->loadWorkflowById($mongoId);                  // echoes "Workflow Not Found" and exits if missing/deleted
$wf->loadWorkflowByShortcode($shortCode, $output = false);
$wf->getWrkflowInfoByName($name);                 // → id
$wf->getWrkflowInfoByShortcode($code, '_id');
```

Caches: `$GLOBALS['WorkflowIdCache']` and `$GLOBALS['WorkflowSCCache']`,
per request.

Listing: `getTunedWorkflows($mode, $appShortCode, $shortCodes)` with `$mode`
one of `reusable` | `apps` | `limit` (the recent 50) | `recent`.

## Running one in PHP

```php
$result = $wf->runWorkflow(
    $parameters,        // [ [key => value, …] ] — becomes output[0]
    'master',           // or 'child'
    $enableLog,         // pass the workflow's own enable_log
    $parentLogId,       // set for a background child
    $executedFrom,      // 'external', 'chat', …
    $masterWorkflowId
);
// → [ 'workflow_exec_id' => int,
//     'activityResult'   => [ 'status', 'output', 'prev_outputs', 'prev_labels', … ],
//     'workflowStatus'   => [ '## Starting Workflow.....', … ],
//     'jsCodes'          => [ … ] ]
```

`Workflow::run($workflowId, $nextActivityId, $activityResult)` is a leaner
variant that skips logging — used for resuming from a specific block.

Guards inside the loop: the workflow is re-checked for deletion at the start,
`blockRunCount > 10000` throws `WorkflowError` ("Infinite Loop proection"), and
any block exception is rewrapped as `WorkflowError` with file and line.

## Child workflow discovery

`getChildWorkflowInfo($wrkflwRow, $idArrays)` walks `executeworkflow` blocks
recursively to build the tree, **skipping deleted children, de-duplicating, and
setting `invalidConfigureWrkflwLoop` when it detects a cycle**. It stashes the
flattened id list in `session('list_child_workflowids')`. Related endpoints:
`/workflow.getchildlist`, `/workflow.childworkflowlist`.

## Finding workflows by what they contain

Aggregation helpers on `Workflow`:

- `getFormWorkflowList($formId)` — matches
  `w_objects.type == 'formrule'` and
  `w_objects.block_properties.form-config.formId == $formId`
- `getRuleengineWorkflowList($wid, $lapId)` — `$unwind`s `w_objects`, matches
  `ruleengine`, optionally `$elemMatch` on `block_properties.liveapp-id`, then
  `$group`s back by `_id`

The same shape is how you find, say, every workflow touching one spreadsheet:

```js
db.VizWorkflow.aggregate([
  { $match: { _tid: 11, deleted: { $ne: 'true' } } },
  { $unwind: '$w_objects' },
  { $match: { 'w_objects.block_properties.s_master_ssid': '<ssid>' } },
  { $project: { name: 1, short_code: 1, block: '$w_objects.id' } },
]);
```
